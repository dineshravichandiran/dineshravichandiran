Production systems fail for a reason, not by chance — find the actual root cause and the failure stops recurring, permanently. That's the job: incident response, root-cause engineering, and turning repeat manual fixes into automation that doesn't need a human at 2 a.m. Call it the Sherlock Holmes school of ops — the alert is never the crime, just the first clue.

I ship working systems, not slide decks about them. Where something has been run for real, the repo has the evidence; where it has not, the entry says so.

### 🎯 Core Capabilities

Six things I actually do, not six things I studied:

- **Incident Response** — Real pressure, real production, across AWS & Azure. No dress rehearsal.
- **Root Cause Analysis** — Logs are clues, not conclusions. Same method as a detective: gather the evidence, rule out the obvious suspect, find the one that actually did it.
- **Kubernetes Troubleshooting** — CrashLoopBackOff, OOMKilled, scale-downs — diagnosed and resolved with kubectl & k9s, not guessed at.
- **Linux & Middleware Administration** — Fleets, not laptops. Apache, Tomcat, directory services, hardened at scale.
- **Monitoring & Observability** — Own the alert lifecycle end-to-end. If it's not validated before go-live, it's not monitored.
- **Process & Automation** — A recurring incident is a bug in the *process*. Fix that, not just the symptom.

Same loop every time — a live production incident, or one of the automated reactors in the projects below:

```mermaid
flowchart LR
    A[🚨 Alert fires] --> B[🔍 Triage & scope]
    B --> C[🩺 Root cause analysis]
    C --> D[🛠️ Fix or escalate]
    D --> E[📘 Runbook / automate it]
    E --> F[✅ Verify & close]
    F -.->|prevents the repeat| A
```

### 🚀 Featured Projects

A repo that doesn't run isn't a project, it's a claim. Everything below is code you can read, and each entry says plainly how far it has been verified. Grouped the way SRE roles screen: cloud and IaC that was applied for real, then agentic and AIOps tooling, then reliability and automation labs.

#### ☁️ Cloud & Infrastructure as Code — applied to real accounts, drilled, destroyed (evidence in each repo)

- ♻️ **[Self-Healing Infrastructure on AWS](https://github.com/dineshravichandiran/cloud-devops-projects/tree/main/self-healing-aws-infra)** — Terraform VPC/ALB/Auto Scaling Group with CloudWatch alarms and Lambda auto-remediation for failures ASG health checks alone don't catch. Drilled with real failures (ASG replacement, Lambda restart, alarm → Lambda → ASG chain), then destroyed; running it found and fixed four defects.
- 🏗️ **[AWS SRE Platform in Terraform](https://github.com/dineshravichandiran/aws-sre-platform-terraform)** — VPC, ALB, ECS Fargate and RDS as modules, remote state, GitHub Actions authenticating through OIDC (no stored AWS keys), checkov in CI. Five failure drills (task kill, drift detection, state lock, bad release rolled back), then destroyed.
- 🌐 **[AWS Hub-and-Spoke Network in Terraform](https://github.com/dineshravichandiran/aws-hub-spoke-network-terraform)** — Transit Gateway hub with central NAT, isolated spokes, private DNS and Reachability Analyzer paths. The first real run found two bugs (ping blocked by a network ACL; spokes not isolated because traffic hairpinned through the hub NAT), both fixed and re-verified. A second run drilled a network-ACL deny and a flow-log REJECT record.
- ☸️ **[EKS + Argo CD GitOps Platform](https://github.com/dineshravichandiran/cloud-devops-projects/tree/main/eks-gitops-platform)** — Terraform for a private-node EKS cluster that Argo CD runs workloads on. Applied once, an Argo CD self-heal drill run, destroyed, account checked for leftovers.
- 🔐 **[Azure Secure Web App in Bicep](https://github.com/dineshravichandiran/cloud-devops-projects/tree/main/azure-secure-webapp-bicep)** — App Service reading a secret from Key Vault through a Key Vault reference with its own managed identity (no stored credentials), logs to Log Analytics and Application Insights. Applied once to Azure: removing the role made the app return 503 `AccessToKeyVaultDenied` after about 12 minutes, restoring it brought 200 back; destroyed with a clean leftover check. The write-up also records a bug in my own first drill script.
- 🔄 **[Azure DevOps Pipeline](https://github.com/dineshravichandiran/azure-iac-bicep/tree/main/azure-devops-pipeline)** — multi-stage pipeline (build, security checks, Bicep provisioning, dev → staging → production with approvals and slot swaps). **Run end to end on a real Azure DevOps organization on 2026-11-21, then destroyed:** three runs failed for real reasons and were fixed, the fourth went green. Production ran S1, not P1v3 (trial quota).

#### 🤖 Agentic SRE & AIOps

- 🧰 **[Ops MCP Server](https://github.com/dineshravichandiran/cloud-devops-projects/tree/main/ops-mcp-server)** — an MCP server that lets an AI agent read AWS and Kubernetes while on call; writes need a person to approve that exact change first, once. 33 tests in CI (stubbed AWS and kubectl); read-only AWS calls checked on a live account.
- 🛡️ **[Guardrailed SRE Incident-Response Agent](https://github.com/dineshravichandiran/agentic-sre-responder)** — rule-based planner, JSON-output LLM planner and a tool-calling LLM agent behind one guardrail layer (restart limits, healthy-metrics check, human hand-off). Seven-scenario evaluation; tests fail when each safety check is removed.
- 🔎 **[AI Incident Triage Agent](https://github.com/dineshravichandiran/ai-incident-triage-agent)** — filters alert logs, names the likely cause, retrieves the runbook step and drafts the note; any fix needs a human-issued approval enforced in code. On 20 frozen incidents, filtered context cut input tokens 91% at equal accuracy; hybrid BM25 + embedding retrieval ranked the right runbook first in 42 of 50 test queries against 39 for BM25 alone.
- 🤖 **[AIOps Alert Correlation & RCA Engine](https://github.com/dineshravichandiran/aiops-alert-correlation)** — sliding-window correlator (76.9% noise reduction, 13,833 raw alerts → 3,197 incidents on a synthetic set), an IsolationForest anomaly detector and a RandomForest root-cause classifier (56.8% accuracy vs. ~12.5% random baseline). 8 passing tests.

#### ⚙️ Reliability, Observability & Automation Labs

- ☸️ **[Kubernetes Self-Healing & Chaos Lab](https://github.com/dineshravichandiran/k8s-self-healing-lab)** — a controller that detects and auto-remediates CrashLoopBackOff and OOMKilled; chaos scripts trigger both. Verified live in a kind cluster in a GitHub Codespace: triggered, detected and remediated within seconds, fully logged.
- 🛠️ **[Runbook Automation Engine](https://github.com/dineshravichandiran/runbook-automation-engine)** — executable YAML runbooks (check, remediate, verify) with dry-run and a JSON audit log. Verified live against a real memory leak, a real full disk and a real crashed service. 5 passing tests.
- 🧠 **[Salt Self-Healing Memory Guard](https://github.com/dineshravichandiran/salt-self-healing-memory)** — a custom Salt beacon watches a service's memory and a reactor restarts it before an OOM kill. Three consecutive detect → restart → log cycles verified.
- 🔐 **[End-to-End DevSecOps CI Pipeline](https://github.com/dineshravichandiran/devsecops-ci-pipeline)** — GitHub Actions running secret scanning, SAST, SCA, container scanning and DAST on every push, findings in the Security tab. Found and fixed three real failures; all 8 jobs run green. Trivy and ZAP are report-only so far; the staging deploy and policy gate are still placeholders. - 📊 **[Grafana + Prometheus Observability Stack](https://github.com/dineshravichandiran/grafana-observability-stack)** — dashboards and alert rules provisioned entirely as code over a synthetic exporter; verified running live in a GitHub Codespace.
